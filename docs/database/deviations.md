# Database deviations from Deliverable 2

Every intentional difference between the Deliverable 2 design and the deployed schema is recorded
here with its rationale. The full ERD and data dictionary are added by SD-012.

| #   | Area                 | Deviation                                                                                                                                                                                              | Rationale                                                                                                                                                                                                                                |
| --- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Repository layout    | Prisma schema, migrations and config live in `backend/prisma/` (as the E01 issues specify); the generated client is emitted to `packages/db/src/generated` so backend and worker share it.             | Keeps the issue paths while preserving the E00 `@smartdesk/db` client package used by both processes.                                                                                                                                    |
| 2   | Timestamp precision  | `TIMESTAMPTZ(6)` (microseconds, PostgreSQL's native precision) and `DEFAULT CURRENT_TIMESTAMP` (equivalent to `NOW()`).                                                                                | This is what Prisma emits for `Timestamptz(6)` / `@default(now())`; semantics match the dictionary.                                                                                                                                      |
| 3   | Enumerated columns   | `role`, `status`, `priority`, `review_status`, `event_type` are `VARCHAR` columns, not PostgreSQL enums or Prisma enums. Allowed values are enforced by CHECK constraints (SD-007).                    | The dictionary specifies `VARCHAR(n)`; CHECKs are easier to evolve by migration than enum types.                                                                                                                                         |
| 4   | Foreign-key update   | Prisma generates `ON UPDATE CASCADE` on foreign keys; every `ON DELETE` is `RESTRICT`.                                                                                                                 | Keys are immutable UUIDs, so update cascade is inert. Deletes never cascade, preserving history.                                                                                                                                         |
| 5   | Credentials (SD-013) | `users` gains `password_hash VARCHAR(255) NULL` (Argon2id only, CHECK) and `token_version INTEGER NOT NULL DEFAULT 0`. **No refresh-session / token-family table**, unlike issue #25 as first written. | Authentication is stateless JWT (see `docs/auth.md`): revocation is per user via `token_version`, so there is nothing to store or clean up per session. Columns on `users` (the issue allows this) avoid a 1:1 table for two attributes. |

## Constraint enforcement (SD-007)

Migration `0002_constraints_indexes` adds the rules Prisma cannot express. It was produced from the
Prisma schema (`@@index`, `@@unique`, and the composite relation) plus hand-written SQL for the CHECKs
and the trigger. `prisma migrate diff` reports no drift between the schema and the migrated database.

| Rule                                                                              | Enforced by                                                                            | Notes                                                                                                                                                                                                                                                                            |
| --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Role, status, priority, review status, event type value sets                      | SQL CHECK (`ck_*`)                                                                     | Event codes: CREATED, STATUS_CHANGED, TEAM_ASSIGNED, TEAM_REASSIGNED, COMMENT_ADDED, AI_REVIEWED, RESOLVED, REOPENED, plus `CATEGORY_UPDATED`, `PRIORITY_UPDATED`, `ASSIGNEE_UPDATED` (the issue required "category/priority updates"; assignee changes added for completeness). |
| Lowercase unique nonblank email; nonblank names/titles/bodies/model version       | SQL CHECK + UNIQUE                                                                     | Blank means empty after `btrim`.                                                                                                                                                                                                                                                 |
| Assignee belongs to the assigned team                                             | Composite FK `tickets(assigned_team_id, assignee_id) → team_members(team_id, user_id)` | `MATCH SIMPLE`: PostgreSQL skips the check when either column is NULL. `ck_tickets_assignee_requires_team` closes the gap (no assignee without a team). A team with no assignee is valid.                                                                                        |
| TRIAGED / IN_PROGRESS need category, priority ≠ UNSET and team                    | SQL CHECK                                                                              |                                                                                                                                                                                                                                                                                  |
| RESOLVED / CLOSED need nonblank summary and `resolved_at ≥ created_at`            | SQL CHECK                                                                              | Also, unresolved statuses must have both resolution fields NULL, so reopening must clear them. Earlier RESOLVED/REOPENED events remain.                                                                                                                                          |
| Allowed status transitions (OPEN → TRIAGED → … , reopen edges)                    | Service layer (SD-008 / #32)                                                           | A CHECK can validate only the final row, not the edge taken.                                                                                                                                                                                                                     |
| Review completeness (PENDING ⇒ no reviewer/time; reviewed ⇒ both; time ≥ created) | SQL CHECK                                                                              |                                                                                                                                                                                                                                                                                  |
| `ticket_events` is append-only                                                    | Trigger `trg_ticket_events_append_only`                                                | Blocks UPDATE and DELETE for every role. TRUNCATE is not a row operation and is not blocked; it is reserved for test resets and administrators.                                                                                                                                  |
| No cascading deletes                                                              | All FKs `ON DELETE RESTRICT`                                                           | Users, teams and categories are deactivated, not deleted.                                                                                                                                                                                                                        |

All CHECKs permit the manual-AI-fallback workflow: a ticket can be triaged with no `ai_recommendations` row.
